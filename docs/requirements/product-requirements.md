# 产品需求规格书 PRD + 需求追踪矩阵

**USS-PRD-001｜v0.1.0-draft｜2026-10-08｜状态：设计评审｜适用：Windows x64 Desktop MVP**

## 1. 产品定位与角色
产品名：Userscript Self-Healing Manager（USSHM）。**用户利益**：将人工逐份请求 Codex 分析脚本，转换为本地批量发现→证据定位→候选修复→受控验证→批准应用的工作流。核心用户：脚本作者、同时维护多个站点脚本的高级用户、需要修复记录的维护人员。角色模式：单机 Owner（首期）、可选 Viewer/Reviewer（未来）；不做云账号或多人实时同步。

## 2. 约束与统一定义
- **MUST/P0**：未满足不允许发布 MVP；**SHOULD/P1**：正式 1.0 目标；**COULD/P2**：扩展阶段。
- `pass` 表示有检查步骤和证据；`unknown` 不等于 `pass`；`repaired` 不等于 `validated`。
- 本地分析不执行 JS；动态测试运行的脚本及页面视为潜在不可信，需授权。
- 所有批量操作“失败隔离、可暂停、可恢复、可追踪”。
- 在没有目标网页可访问、没有登录会话、没有功能契约时，报告必须严格标识受阻而非成功。

## 4. 非功能要求（建议目标）
| ID | 要求 | 验收 |
|---|---|---|
| NFR-001 | 默认安全 | AI 默认关闭；不会自动执行危险页面动作；不会访问未知目标 |
| NFR-002 | 本地隐私 | 仅本地分析路径和报告；Cookie/token/input value 在默认快照中被清理 |
| NFR-003 | 可靠性 | 断电/强制退出时原文件不损坏；恢复交易日志；逐脚本一致性 |
| NFR-004 | 可移植性 | 支持中文/英文/空格/Unicode 路径及无管理员权限操作 |
| NFR-005 | 可测试性 | CDP/文件/AI Provider 可用假对象；重要功能有确定性 fixtures |
| NFR-006 | 可维护性 | 独立模块 API，数据 schema 显式版本，强类型，必要诊断码固定 |
| NFR-007 | 性能 | 目标：导入 100 份各不超过 200KB 脚本的静态索引以实测基线为准，不设虚假毫秒保证 |
| NFR-008 | 并发 | 同网站/同浏览器 profile 默认单动态任务；静态分析可配置并发；预算与取消生效 |
| NFR-009 | 体验 | 列表可筛选、状态可读、进度真实；每次长操作可取消且能看到失败原因 |
| NFR-010 | 合规 | 遵守浏览器和网站安全限制；明确操作权限，保留本机报告清理控制 |
| NFR-011 | 可恢复性 | 每次成功覆盖都可选备份恢复且需 hash 验证；冲突禁止静默覆盖 |
| NFR-012 | 外部依赖 | 锁定依赖版本、生成 SBOM、CI 安全扫描；秘密不进入 repo |
| NFR-013 | 兼容性 | 独立检测所选 Chrome 的实际 CDP 可用性；不能从文件名推断支持 |

## 5. 核心 User Stories
- **US-01** 作为用户，我可以指定任一有效 Chrome executable 或 portable launcher，并在执行前看到连接是否真的成功。
- **US-02** 作为用户，我一次拖入 30 份脚本，立即知道哪些源码需要运行时确认，哪些元数据/语法存在问题。
- **US-03** 作为用户，发现 ChatGPT 输入框改动，我能看到过去 selector、当前 DOM 候选、修复解释和受影响的全部脚本。
- **US-04** 作为用户，点击“批量修复”后，我知道哪些完成了代码更改、哪些只通过了 DOM 级检查、哪些因未登录而阻断。
- **US-05** 作为用户，可以在没有上传任何敏感资料的情况下先做全部本地检测，并选择是否让 AI 协助处理困难 case。
- **US-06** 作为用户，任何一个修复版本失效，都能按版本和日期回退，而不是人工找备份文件。
- **US-07** 作为用户，我能查看“昨天正常、今天失效”所依据的证据，而不是一个笼统的红色失败状态。

## 6. MVP 严格边界
MVP **必须完成** FR-001~005、007~016、018~025、027~030、039~041；可保留首期排除的 P1 UI 入口但必须标 `not-implemented`，不可展示为可用。FR-017/026/031~038/042/045 进入 1.0 迭代；P2 在 1.x 以后安排。若早期评审发现用户最常见脚本高度依赖 GM API，则 **FR-026 升为 MVP 阻断项**，不能以纯 CDP 注入结果代替。

## 7. 需求变更与验收规则
每项需求应在 GitHub Issue 中填写 `FR-ID`、优先级、用户价值、接口契约、风险、对应测试、证据与负责人；状态：`proposed → specified → planned → in-progress → in-review → verified → released`。新增字段不得破坏已保存 schema；不允许仅凭 UI 手动点击说明即标为自动化测试通过。

## 8. 非承诺说明
所有性能数字、修复评分与测试数据基线均为**待测设计目标**；项目在规格阶段不应把它们写成已实现功能、实际实验结果或质量保证。
